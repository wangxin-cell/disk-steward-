# Safety, privacy and issue reporting

Disk Steward is an alpha. Copying preserves sources; the distinct native-Windows source-release operation permanently removes only the files named in its separately reviewed plan. Review exact actions before applying them. It is not general garbage collection. Tests do not establish protection from every Windows filesystem feature or from malicious concurrent path changes.

The metadata scanner does not read file contents or make network calls. Reports contain paths, sizes, timestamps and volume information. Copy planning and execution read contents for hashing. The scripts do not upload files. A cloud harness/model can receive reports you share with it; its policies and settings govern that data.

Keep reports outside the source and destination and out of public issues. Treat all paths and generated data as untrusted input. Report scan errors and skipped entries; never claim complete coverage after an incomplete scan.

Optional application inventories read the fixed local-machine/current-user uninstall-registration keys in two requested registry views. Only display metadata and installation locations are collected; uninstall commands are neither queried nor executed. No registry writes or application-file reads occur. Inventories can reveal application usage and private locations, so keep them local and out of public issues. Imported registration data is unauthenticated and can be stale. Lexical location overlap is not proof of present installation, exclusive ownership or safe cleanup; unmatched paths remain unknown. Partial collection and limited registration coverage cannot establish absence. See [application evidence](skills/disk-steward/references/application-evidence.md).

The decision-report renderer reads only the supplied plan and optional choices JSON, and exclusively creates one Markdown output. It does not inspect or execute paths embedded in those inputs. Proposals are not permissions; declared destination volume identities are not live filesystem evidence. Escaping report text prevents Markdown/HTML formatting from being interpreted as active report structure, but it does not make the underlying text trustworthy instructions for an agent.

Copy operations target ordinary user-controlled quiescent directories. They preserve sources and reject unsupported cases rather than pretending to be a full NTFS backup. Source ACLs and application integration are not guaranteed. A successful content hash is not permission to delete a subsequently changed source. A plan ID detects modifications relative to the reviewed plan; it is not a cryptographic authorization signature.

Source release verifies a successful copy receipt, rehashes both current trees/selections, then locks and hashes each source/target pair before marking the source handle for deletion. It keeps the retained target locked until source close. There is no unlocked fallback, recursive deletion, Recycle Bin, or automatic undo. Source directories and unselected files stay. The operation is not atomic across files: earlier removals persist after later failure. The append-only JSONL journal records intent and completion; an unfinished log requires reconciliation, not automatic retry. A real backup policy remains necessary for device failure or later target edits.

Native Windows can explicitly opt into `Zone.Identifier` preservation in schema 3 copy plans. The marker is opaque, capped at 64 KiB, hashed separately and verified on the empty target before primary content is written. No marker stripping or sidecar fallback is provided. Other observed ADS and all directory ADS are rejected; default/legacy plans and cache adapters retain strict ADS exclusion. Source release holds the retained marker against writes/deletion; a source marker must share deletion and is checked for observable DeletePending. Windows locks apply per stream and do not freeze new-stream creation, so an unknown ADS added between the final inventory check and source deletion can still be lost. This limitation also applies to a previously stream-free file. Run only after closing writers on user-controlled quiescent files; do not claim protection against hostile concurrent stream mutation. See [marker semantics](skills/disk-steward/references/zone-identifier.md).

The optional pip-cache adapter trusts the already installed interpreter and pip 25.3. It freezes the runtime identity and bounded cache metadata, ignores pip configuration, and reconstructs a fixed purge command rather than executing JSON-supplied arguments. An explicit cache override is not proof of ownership. Close all cache writers; preflight link checks do not protect against hostile concurrent path swaps. Pip's purge can be partially destructive before failure and removes offline reinstall material. Its JSON receipt can be incomplete after a power loss; unlike the source-release JSONL journal it is not an append-only audit trail. Do not auto-retry uncertain results.

Offline release archives use an explicit file allowlist and exclude raw local reports, work directories, bytecode and Git metadata. The SHA-256 manifest detects byte changes but is not an authenticity signature. Review package contents before public distribution.

For a potential data-loss bug, stop using the affected operation and retain the plan/receipt privately. Check the repository's Security tab for private vulnerability reporting, if enabled, or use a private contact channel published by a maintainer. This document does not advertise a private reporting address or promise that GitHub private reporting is enabled. If no private channel is available, request one in an issue without including vulnerability details, personal paths, credentials or file contents.
